# Web アプリの開発の流れ

Web アプリ (`web/`, `server/`) を開発するときの手順をまとめる.
C++ の部分 (`core/`, `cli/`, `android/`) には適用しない.

人が読むのは計画だけで, テストや差分は読まない. そのため AI は次の 2 つを守る.

- 計画を承認されてから実装する.
- コミットの前に必ず検査を通す.

## 機能の単位

開発は機能の単位で進める. 機能とは, 利用者から見て 1 つの操作が端から端まで動くまとまりのこと.
大まかな機能の一覧は [web-app.md](web-app.md) の「操作と条件」の表にある. 表の 1 行が 1 つの機能になる.

1 つの機能には, その操作に要るものを層をまたいでまとめて入れる. たとえば「参加する」なら次のとおり.

- DB: Player の表と, 名前の重なりを禁じる制約
- 規則: 名前の決まりを確かめる関数
- API: `POST /matches/{id}/players`
- 画面: 参加の画面と, トークンをブラウザに保存する処理
- テスト: 上の動きを確かめるもの

層ごとに作る (先に DB を全部作り, 次に API を全部作る) ことはしない. 最後まで何も動かず, 問題がまとめて後から出るため.

## 手順

### 1. 計画を作り, 承認を得る

実装を始める前に計画を人に示し, 承認を得る. 承認されるまでコードを書かない.

計画には次のことを書く.

- 作る機能と, その順番. 複数の機能を 1 つの計画に入れてよい.
- 機能ごとに変える・作るファイル.
- 機能ごとのテストの観点. テストのコードではなく, 何を確かめるかを日本語の箇条書きで書く.
  人はテストのコードを読まないので, 何が保証されるかはここでしか分からない.
  例: 「名前が 21 文字なら参加を拒否する」「最初のラウンドを始めたあとは参加を拒否する」.
- コミットの分け方.

承認されたら, 実装を始める前に計画をファイルに残してコミットする.
人の指示と, そのとき承認された計画を, あとから見られるようにするため.
書き方は「計画の記録」にまとめる.

### 2. 実装する

- 計画の順番どおりに, 1 つの機能ずつ進める. 1 つの機能を終えてから次の機能に移る.
- 1 つの機能の中でも, 小さく分けてそのつどコミットする.
  例: 名前の決まりの関数とテスト → DB と API とテスト → 画面.
- テストは必要なら変えてよい. 弱めたり消したりしてもよい.

### 3. 検査を通してコミットする

- コミットの前に, 整形・lint・型検査・全テストを必ず通す. 通らない状態でコミットしない.
- 検査が通らないときは直す. どうしても通せないときは, 止まって人に次のことを説明する.
  - 何が通らないか (エラーの内容).
  - 何を試したか.
  - 原因の見当と, 取れる選択肢.
- コミットは main に直接行う. ブランチと PR は使わない.
- 1 コミット 1 目的にする. メッセージは今の書き方 (`feat:`, `test:`, `docs:` などと日本語の要約) に合わせる.

### 計画を変えるとき

実装の途中で計画どおりに進められなくなったら, 止まって人に説明し, 承認を得る.
計画を変えるとは, 機能やその順番を変えること, 計画にない機能を足すこと, テストの観点を変えることをいう.
計画の範囲の中での細かい作り方は, 人に聞かずに決めてよい.
変更が承認されたら, 計画の記録に追記してコミットしてから実装を続ける.

## 計画の記録

承認された計画は `docs/plans/` に 1 つの計画につき 1 ファイルで残す.

- ファイル名は `YYYY-MM-DD-<内容を表す英語の短い名前>.md` にする. 例: `2026-10-20-join-match.md`.
- 承認されたら, 実装を始める前に `docs: 計画 <内容> を残す` のようなメッセージでコミットする.
- 承認されたあとの計画は書き換えない. 計画を変えたときは「計画の変更」に追記する.
  最初に何を承認したかが分からなくならないようにするため.
- 機能を 1 つ終えたら, その機能の最後のコミットで「進み具合」にチェックを付ける.
  新しいセッションで, どこから続けるかが分かるようにするため.

形式は次のとおり.

```markdown
# <計画の名前>

承認日: YYYY-MM-DD

## 人の指示

<計画を作るきっかけになった人の指示. 言い換えずに原文のまま書く.>

## 計画

<承認された計画. 人に示したものをそのまま書く.>

## 進み具合

- [ ] 機能 1
- [ ] 機能 2

## 計画の変更

### YYYY-MM-DD

- 人の指示: <原文>
- 変更: <何をどう変えたか>
```

## してはいけないこと

Web アプリの作業では, 次のことをしない.

- `web/`, `server/` と, その作業に要る文書 (`docs/` や `CLAUDE.md`) 以外を変えない.
  `core/`, `cli/`, `android/` などの C++ の部分を壊さないため.
- 計画にない依存ライブラリや外部サービスを足さない. 足すなら計画に書いて承認を得る.
  依存が増えるほど, 理解と保守が難しくなるため.
- 決めた技術 (言語, フレームワーク, DB など) を勝手に変えない.
- 検査を飛ばさない. `git commit --no-verify` や, lint・型検査を黙らせる注記 (`@ts-ignore`, `eslint-disable` など) を使わない.
  テストを変えることは許すが, 検査そのものを外すとコミット前の関門がなくなるため.
- 秘密情報 (API キー, Cloudflare などのトークン, `.env`) をコミットしない. 履歴に残ると消せないため.
- デプロイや, 本番の DB の変更・削除は, 人に指示されたときだけ行う. 取り返しがつかないため.
- `git push` をしない. push は人が行う.
- git の履歴を書き換えない (`git reset --hard`, `git rebase`, `git commit --amend`, `git push --force` など).
  main に直接コミットするので, 壊すと戻せないため.
