# Web アプリのセキュリティ

Web アプリ (`web/`, `server/`) で守るセキュリティの規則をまとめる.

このアプリにはログインがなく, マッチの URL を知っていれば参加でき, 本人の確認はブラウザに保存したトークンで行う
([web-app.md](web-app.md)). URL は公開されたインターネットに置く. 規則はこの前提から決めている.

## 識別子とトークン

- **マッチの id は推測できない乱数にする.** 連番や時刻から作らない.
  URL を知っていれば参加できるので, id を推測できると他人のマッチに入れてしまうため.
- **トークンは暗号用の乱数で, 128 ビット以上にする.** `Math.random` のような暗号用でない乱数は使わない.
- **DB にはトークンのハッシュ値を保存する.** トークンそのものは保存しない.
  DB の中身が漏れても, なりすましに使えないようにするため.

## 権限の確認

- 本人か, リーダーかの確認は, 毎回サーバーで行う.
  画面でボタンを隠すだけにしない. 画面の制限は, API を直接呼べば回避できるため.

## 入力

- 外から来る入力は, API の入口で型・範囲・長さを検証する. 知らない項目が入っていたら拒否する.
  不正な値が DB に入らないようにするため.
- SQL には必ずプレースホルダで値を渡す. 文字列の連結で SQL を組み立てない. SQL インジェクションを防ぐため.

## 表示

- 利用者が入れた文字 (名前など) は, エスケープして表示する. `innerHTML` などで HTML として直接入れない.
  XSS を防ぐため. トークンをブラウザに保存するので, XSS を許すとトークンを盗まれる.

## 漏らさない

- ログとエラーの応答に, トークンを出さない.
- エラーの応答に, 内部の情報 (SQL, スタックトレース, ファイルのパス) を出さない. 利用者には何が悪かったかだけを返す.

## 他のサイトからの呼び出し

- CORS で許すのは自分のサイトだけにする. 他のサイトのページから API を勝手に呼ばれないようにするため.
  Android アプリはブラウザではないので, CORS の影響を受けない.

## 大量のデータへの備え

公開された URL なので, 大量のデータを送られても壊れないようにする.

- リクエストの本文の大きさに上限を設ける.
- 1 つのマッチのプレイヤーは 10 人までにする.

## 依存ライブラリ

- 依存ライブラリの既知の脆弱性を, コミット前の検査に含める (`npm audit` など). 古いライブラリの穴を放置しないため.
