## 計画

### 決めたこと

| 項目 | 決めたこと |
|---|---|
| CI | GitHub Actions |
| URL | `pokerchip-score.<サブドメイン>.workers.dev` (無料) |
| デプロイのきっかけ | main への push のうち, 指定のファイル (`web/` の下, `web/detector.lock`, デプロイのワークフロー) が変わったときだけ |
| 検出器 | 手元でビルドして GitHub Releases に置く. CI はタグと sha256 を確かめて取ってくる |
| DB の migrations | 手で起動するワークフローで当てる. 未適用の migration があれば, デプロイは止まる |
| `npm audit` | 本番の依存だけで止める. 開発の道具の脆弱性は表示だけする |
| Workers Logs | 使う |
| `database_id` | 本物の値をコミットする |

### 機能と順番

#### 1. 検査の `npm audit` を本番の依存だけにする

- `web/package.json` の `check` を `npm audit --omit=dev && npm audit --audit-level=none` にする.
- `docs/development/web/typescript.md` に理由を書く.
- テストの観点:
  - 今の状態 (開発の道具だけに high がある) で `npm run check` が通る.
  - 開発の道具の脆弱性は, 出力に表示される.

#### 2. 検出器を Release に出す・取ってくる

- `scripts/release_detector.sh` (手元): 検出器の 3 ファイルの sha256 を計算し, `gh release create` でタグ
  `detector-YYYYMMDD-<core のコミット>` の Release を作り (説明にビルドしたコミットを書く), `web/detector.lock` (タグと sha256) を書き換える.
- `scripts/fetch_detector.sh` (CI と手元): `web/detector.lock` のタグの Release を `gh release download` で取り,
  sha256 を確かめてから `web/src/client/public/detector/` に置く.
- `docs/logic/usage.md` の「WASM」に, Web に出すときの手順を足す.
- テストの観点:
  - 取ってきたファイルの sha256 が `detector.lock` と違えば失敗し, 何も置かない.
  - `detector.lock` のタグの Release がなければ失敗する.
  - 検出器のファイルがそろっていなければ, Release を作らずに止まる.
  - 同じタグがもうあれば, 上書きせずに止まる.

#### 3. デプロイのワークフロー (`.github/workflows/deploy.yml`)

- checkout と Node 24 → `npm ci` → 検出器を取ってくる → `npm run check` → 未適用の migration がないかを確かめる → `npm run build` → `npx wrangler deploy`.
- 外部の action はコミットの SHA で固定する. 権限は `contents: read` だけにする. 同時に 2 つのデプロイが走らないようにする (`concurrency`).
- `web/wrangler.toml` に `[observability] enabled = true` を足す (Workers Logs).
- テストの観点:
  - `docs/` だけを変えた push では動かない. `web/` を変えた push では動く.
  - `npm run check` が失敗すれば, デプロイしない.
  - 未適用の migration があれば, 「migration のワークフローを先に起動してください」と出して止まる.
  - 最初のデプロイのあと, 画面の確かめ (マッチを作る, 参加する, `/count` でチップを検出する) を人に依頼する.

#### 4. migration のワークフロー (`.github/workflows/migrate.yml`)

- 手でボタンを押したとき (`workflow_dispatch`) だけ動き, `npx wrangler d1 migrations apply DB --remote` を実行する.
- テストの観点:
  - push では動かない.
  - 起動すると未適用の migration が当たり, そのあとのデプロイが通る.

#### 5. 文書

- `docs/web/running.md` の「デプロイ」: 最初の 1 回の手順, ふだんの流れ, migration を足したとき, 検出器を出し直すとき, 戻し方 (`wrangler rollback`, Time Travel).
- `docs/architecture.md`: 「デプロイ」の節を足し, 検出器を Release から取る理由と, migration を手で起動する理由を書く.
- `docs/development/web/process.md`: 「デプロイは人の指示で」を「人の push がデプロイになる. AI は push しないので AI がデプロイすることはない.
  migration のワークフローを起動するのも人だけ」に合わせて書き直す.
- `docs/worklog.md`: CI の追加を記録する.

#### 6. 本番の `database_id` を入れる

- 人が D1 を作ったあと, `web/wrangler.toml` に本物の番号を入れてコミットする.

### 人がすること

1. Cloudflare のアカウントを作り, `npx wrangler login` でログインする.
2. `cd web && npx wrangler d1 create pokerchip-score` で D1 を作り, 番号を AI に伝える.
3. API トークンを作る. 権限は「Workers Scripts: Edit」と「D1: Edit」だけ, 対象はこのアカウントだけ.
4. GitHub の Secrets に `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` を登録する.
5. 最初の検出器の Release を作る (`scripts/release_detector.sh`). GitHub に公開する操作なので, 人が実行するか, AI に実行を指示する.
6. migration のワークフローを起動し, push する.

### 決まりの例外

この計画に限り, `web/` と `docs/` などの外の `.github/workflows/`, `scripts/release_detector.sh`, `scripts/fetch_detector.sh`,
`docs/logic/usage.md`, `docs/architecture.md` を変えてよい. 依存ライブラリは足さない. 外部のサービスとして GitHub Actions と GitHub Releases を足す.

### コミットの分け方

1. `docs: 計画 GitHub Actions で Cloudflare にデプロイする を残す`
2. `chore: 検査の npm audit を本番の依存だけで止める`
3. `feat: 検出器を GitHub Releases に出すスクリプトと, 取ってくるスクリプトを足す`
4. `ci: main への push で Cloudflare にデプロイするワークフローを足す`
5. `ci: 本番の D1 に migration を当てる, 手で起動するワークフローを足す`
6. `docs: デプロイの手順と設計を書く`
7. `chore: 本番の D1 の database_id を入れる` (人が D1 を作ったあと)
