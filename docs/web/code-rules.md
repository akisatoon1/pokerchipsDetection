# Web アプリのコードの書き方

Web アプリ (`web/`) のコードを書くときの規則をまとめる.
目的は 2 つある.

- **変えやすいこと**: 1 つの変更が 1 か所で済み, ほかの場所を壊さない.
- **読みやすいこと**: 後から人が読んで, 何をしているか, なぜそうしているかが分かる.

人は差分を読まないので, 読まれなくても後で読める状態を保つ.
言語やフレームワークに固有の書き方は, 技術を決めたあとに別にまとめる.

## モジュールの分け方

### 規則と入出力を分ける

点数の計算や名前の決まりのような規則は, 純粋な関数 (引数だけから結果を返し, DB・HTTP・画面に触れない関数) にする.
規則が変わったときに直す場所が 1 か所で済み, DB やサーバーを立てずにテストできるため.

### 層と依存の向き

コードを次の層に分け, 依存は矢印の向きにだけ持つ. 逆向き (規則が API を知るなど) の依存は作らない.

```
画面 ──HTTP──→ API ──→ 規則
                └────→ DB アクセス
```

| 層 | 役割 | してはいけないこと |
|---|---|---|
| 画面 | 入力を受けて API を呼び, 結果を表示する | 点数の計算などの規則を持つ. 規則は API の結果を使う |
| API | 入力を検証し, 規則と DB アクセスを呼び, 応答の形に変える | 規則の中身を書く. SQL を直接書く |
| 規則 | 計算と判定 | DB・HTTP・画面に触れる |
| DB アクセス | データの読み書き. SQL はここにだけ書く | 規則の判定をする |

### まとめ方

- 同じ理由で変わるものは近くに置き, 違う理由で変わるものは分ける.
- モジュールの外に公開する (export する) のは, 外から使うものだけにする.
- DB の接続などの外部のものは, 関数の中で作らず引数で受け取る. テストで差し替えられるようにするため.
- 外から来る入力 (HTTP の本文など) は API の入口で検証する. 内側の層は検証済みの値だけを受け取る.
- 設定値や上限 (名前の長さ 20 文字など) は定数として 1 か所に置き, 名前を付けて使う. 同じ数字を何か所にも書かない.

### 共通化

- 似たコードが 2 か所にあるだけでは共通化しない. 3 か所目が出て, 同じ理由で変わると分かってから共通化する.
  早すぎる共通化は, 片方だけ変えたいときに足かせになるため.
- 今使わない拡張のための仕組み (将来のための引数, 使われない抽象化) を作らない.

## 読みやすさ

### 名前

- 何を表すかが分かる名前にする. 意味の分かりにくい略語は使わない.
- 用語は [app.md](app.md) と [scoring.md](scoring.md) に合わせ, 同じものには同じ名前を使う.
  たとえば Match, Player, Round, Entry, 初期点数, 持ち点, 増減, 累計.
- 真偽値は `is`, `has`, `can` などで始め, 何が真なのかが分かるようにする.

### 関数

- 1 つの関数は 1 つのことだけをする. 名前で説明しきれないなら分ける.
- 長さは 40 行程度まで, 入れ子は 3 段までを目安にする. 条件に合わない場合は早めに return して入れ子を浅くする.
- 引数が 4 つを超えるなら, オブジェクトにまとめる.

### 書き方

- 短さや巧みさより, 素直で読みやすい書き方を選ぶ.
- 同じことは, 既存のコードと同じ書き方で書く. 新しい書き方を持ち込むときは, 既存の箇所もそろえる.
- エラーを握りつぶさない. 捕まえたら, 処理するか, 意味の分かる形で上に伝える.
- 使われなくなったコードは消す. コメントアウトして残さない (履歴は git にある).

### コメント

- 何をしているかはコードで表し, コメントには **なぜそうするか** を書く.
- 外に公開する関数と型には, 役割と, 引数・戻り値・失敗したときの振る舞いを書く.
- 仕様や決めたことに由来するコードには, その理由を書く. 例: 「確定したラウンドは変更できない (リーダーの確定は取り消せない仕様のため)」.
