# コードの書き方

C++ (`core/`, `cli/`, JNI), Kotlin (`android/`), TypeScript (`web/`) のすべてのコードで守る, 言語によらない規則をまとめる.
目的は 2 つある.

- **変えやすいこと**: 1 つの変更が 1 か所で済み, ほかの場所を壊さない.
- **読みやすいこと**: 後から人が読んで, 何をしているか, なぜそうしているかが分かる.

差分を読まなかった人が後から読んでも分かる状態を保つ.
言語に固有の書き方は [cpp-coding-style.md](cpp-coding-style.md), [android/kotlin.md](android/kotlin.md),
[web/typescript.md](web/typescript.md) に, Web の層の分け方は [web/layers.md](web/layers.md) にある.

## モジュールの分け方

### 規則と入出力を分ける

点数の計算, チップの色の判定, 名前の決まりのような規則は, 純粋な関数 (引数だけから結果を返し, 入出力に触れない関数) にする.
入出力とは, ファイル, DB, HTTP, 画面, OS やフレームワークの API (Android の Context など) のこと.
規則が変わったときに直す場所が 1 か所で済み, 入出力を用意せずにテストできるため.

依存は入出力の側から規則に向ける. 規則が入出力を知る逆向きの依存は作らない.

### まとめ方

- 同じ理由で変わるものは近くに置き, 違う理由で変わるものは分ける.
- モジュールの外に公開する (ヘッダに宣言する, export する, `private` にしない) のは, 外から使うものだけにする.
- DB の接続やファイル, モデルのような外部のものは, 関数の中で作らず引数で受け取る. テストで差し替えられるようにするため.
- 外から来る入力 (HTTP の本文, 画像, 端末に保存した値, コマンドラインの引数など) は入口で検証する.
  内側の処理は検証済みの値だけを受け取る.
- 設定値や上限 (名前の長さ 20 文字など) は定数として 1 か所に置き, 名前を付けて使う. 同じ数字を何か所にも書かない.

### 共通化

- 似たコードが 2 か所にあるだけでは共通化しない. 3 か所目が出て, 同じ理由で変わると分かってから共通化する.
  早すぎる共通化は, 片方だけ変えたいときに足かせになるため.
- 今使わない拡張のための仕組み (将来のための引数, 使われない抽象化) を作らない.

## 読みやすさ

### 名前

- 何を表すかが分かる名前にする. 意味の分かりにくい略語は使わない.
- 用語は仕様の文書 ([../architecture.md](../architecture.md), [../web/app.md](../web/app.md), [../web/scoring.md](../web/scoring.md)) に合わせ,
  同じものには同じ名前を使う.
- 真偽値は `is`, `has`, `can` などで始め, 何が真なのかが分かるようにする.

### 関数

- 1 つの関数は 1 つのことだけをする. 名前で説明しきれないなら分ける.
- 長さは 40 行程度まで, 入れ子は 3 段までを目安にする. 条件に合わない場合は早めに return して入れ子を浅くする.
- 引数が 4 つを超えるなら, 1 つの型 (構造体, data class, オブジェクト) にまとめる.

### 書き方

- 短さや巧みさより, 素直で読みやすい書き方を選ぶ.
- 同じことは, 既存のコードと同じ書き方で書く. 新しい書き方を持ち込むときは, 既存の箇所もそろえる.
- エラーを握りつぶさない. 捕まえたら, 処理するか, 意味の分かる形で上に伝える.
- 使われなくなったコードは消す. コメントアウトして残さない (履歴は git にある).

### コメント

- 何をしているかはコードで表し, コメントには **なぜそうするか** を書く.
- 外に公開する関数と型には, 役割と, 引数・戻り値・失敗したときの振る舞いを書く. 書式は言語ごとの文書に従う.
- 仕様や決めたことに由来するコードには, その理由を書く. 例: 「確定したラウンドは変更できない (リーダーの確定は取り消せない仕様のため)」.
